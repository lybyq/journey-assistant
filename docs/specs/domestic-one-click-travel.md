# 国内一键出行助手改造 Spec

状态：工程链路已实现，商业商品接口待授权；调研日期：2026-10-30；验收更新：2026-10-31；范围：中国内地出行，人民币、Asia/Shanghai。国外以及港澳台的跨境票务/证件流程另立 spec。技术栈沿用 NestJS、TypeScript、Deep Agents/LangChain、PostgreSQL、Redis、Vue 3/Vite。

## 1. Executive Summary

### 问题与产品定位

目前的产品让用户阅读一篇攻略、手工进入多个业务表单，缺少从需求到比较、选择、预订的连续体验。工具调用成功与产品价值不是一回事。

目标产品是「国内旅行决策与安排助手」：一次表达需求，自动整理信息、查询候选、安排路线与日程，给出有真实差异的方案，解释取舍，并把选中的交通、住宿、餐饮和游玩项目交接给可靠的平台完成预订。用户不用自己跨平台抄资料、配日期、算账、重排路线。

已确认覆盖独行、情侣、朋友、亲子、老人同行等全部个人出行场景；通过约束和偏好区别安排，不用年龄刻板印象替代用户选择。商业模式是免费规划＋预订导流；佣金不能影响对用户宣称的适合程度或最低价。

### 吸引力与收益

| 用户要完成的事     | 本产品应带来的收益                 | 产品证据                     |
| ------------------ | ---------------------------------- | ---------------------------- |
| 不知道怎么安排     | 一次输入得到能继续操作的安排       | 结构化方案，不仅是文字       |
| 很难选交通/住宿    | 解释费用、门到门耗时、强度的取舍   | 可横向比较、有来源的候选     |
| 攻略容易冲突       | 考虑到站、入住、接驳、营业预约窗口 | 独立约束验证，冲突显式呈现   |
| 改一点就全盘重做   | 保留已选项，局部调整并重新算账     | 版本、选中方案和变更影响     |
| 查到后还要重新搜索 | 交接平台，携带实际允许的商品条件   | 区分商品链接、查询入口和导航 |

### 成功标准

以下是验收目标，不能在尚未测试时宣称达到：

1. 对具备足够真实候选的测试项目，生成至少 2 套、最多 3 套有实际差异的方案；只有一套或无解时解释限制，禁止复制一套改标题。
2. 每个展示价格可回溯至来源、条件、金额单位和查询时间；未知项不计为 0，不完整预算只称「已知小计」。
3. 一键规划通过已有持久化运行执行，页面刷新不会丢失结果；输入、公开步骤、版本和选择可以恢复。
4. 可预订按钮 100% 区分商品预订、平台查询、官方入口、地图导航；没有供应商商品链接时不显示「立即购买」。
5. 在 1440×900、1024×768、390×844 验收主要操作，无横向整页溢出；桌面默认内容占主要空间，输入区不长期遮挡方案。
6. 验收不只检查 HTTP 200：覆盖亲子、老人同行、自驾、跟团、售罄、缺授权、价格过期、条件变更、取消、跨用户隔离与恶意跳转。

## 2. User Experience & Functionality

### 用户故事与验收条件

- **REQ-01 一次输入**：用户提供出发地、目的地、日期/天数、成员、预算、兴趣。一键安排先复用已确认需求，只追问影响执行的缺项；国内时区无需反复询问。未确定目的地时提供目的地建议，不伪造库存。
- **REQ-02 多方案**：候选可能来自高铁/飞机/自驾/跟团等不同方式，也可能是同种方式下不同住宿、车次或活动组合。标签为省预算、均衡、舒适，但排名依据必须透明；库存不足时允许少于三套。
- **REQ-03 全程安排**：覆盖门到门交通、每晚住宿、每日活动与餐饮建议、接驳、休息、必要预约。儿童年龄、房间分配、行动能力、饮食、驾车上限按实际条件校验。
- **REQ-04 可比较价格**：酒店同入住/离店/人数/房型/餐食/退改；机票同乘机人、行李、税费与退改；门票同日期、场次、适用人群；餐饮参考人均与团购套餐严格区分。
- **REQ-05 一处修改**：选定方案后换酒店/车次/景点，只重算受影响路线、时间、费用，另存版本；不能把旧预算或预约状态继续当有效。
- **REQ-06 去预订**：展示去平台查询/预订、官方预约和一键导航；外部打开不等于预订成功或付款成功。不收集铁路密码、证件、支付密码或平台 Cookie 来绕过合作权限。
- **REQ-07 可解释的不确定**：明确区分未配置、暂不可用、没有匹配商品、尚未核实、查询阶段到限和报价已过期；它们不能统一称作「没有资源」。
- **REQ-08 工作台**：方案卡片、预算分解、逐日时间轴、地图/导航、预约与预订清单为主体，Markdown 是解释。公开步骤使用真实阶段和工具结果，不展示模型隐藏推理。

### 一键的边界

「一键」是一次触发需求整理、候选查询、组合与校验，再供用户选择。不是自动完成跨平台交易。当前商业目标是跳转平台，由用户确认订单和付款。后续如果开放站内交易，须另写交易、身份、履约、回调及售后 spec。

## 3. AI System Requirements

### 工作流

需求归一与缺项检查 → 供应商能力检查 → 有界并发采集候选 → 同实体/同条件归一 → 候选组合 → 路线与营业/预算独立校验 → 去重并选择至多三套 → 解释与展示 → 用户选择 → 局部修改 → 平台交接。

模型负责理解、解释和调用受控业务工具；金额、版本、硬约束、外链校验由代码决定。复杂规划用一个受控安排工作流减少模型循环与重复搜索；已有查询/模型次数、token 与阶段时间预算仍然生效。外部故障不使已保存候选丢失。

### 上下文

每轮显式注入本账户、本会话的项目摘要：已确认需求、当前版本、方案集合、待确认项、可用供应商。长期偏好只作为默认；当前用户要求优先。版本 ID 是选择依据，不从「第二套」的自然语言标题猜项目；本次方案集合确定显示顺序。对话与方案引用保持归属隔离。

### 生成规则

已有候选不足时禁止为了凑数制造酒店、车次、价格。策略使用真实交通组合、住宿或活动差异；生成签名去重。完整性、已知小计、时长和风险分别展示，不用一个不透明分数掩盖缺价。自由行、自驾、跟团只有在有对应真实数据时才能生成其可执行候选。

接驳采用供应商路线结果，并记录查询时间、出行方式与估算性质。导航服务未返回时标记未核实，不能保留固定 30 分钟却声称真实路线已验证。儿童、老人或行动限制触发约束/提醒，不自动推断免费票、无障碍或体力水平。

### 评估

确定性回归覆盖不同需求、价格口径、方向、缺失数据、去重、CAS、过期与外链。真实联调使用专门测试账户；无商业权限的供应商只验收未配置/不可用状态，不能拿 fixture 当生产库存验收。真实运行保留公开步骤、供应商失败原因和最终结果，单独报告商品覆盖与任务成功率。

## 4. Technical Specifications

### 结构与数据

- `domestic-planning/`：供应商目录、方案组合、安排工作流、平台交接和 HTTP 入口，依赖现有旅行领域服务。
- 共享契约增加市场、策略、供应商状态、方案集合、交接入口；不把模型自由 JSON 直接当商品卡。
- `trip_option_sets` 保存本账户的不可变方案集合与版本 ID、生成时的上下文指纹、限制说明；已有 trip_versions 保留各自价格/来源快照。
- 方案集合指纹与需求/候选变更不一致、生成已超过15分钟或所引用报价有效期已到时显示过期，需要重新查询/安排；选择版本不能默默覆盖新需求。
- 商品报价未来扩展 provider/productId/skuId/conditionHash/amountMinor/priceType/availability/fetchedAt/expiresAt/bookingUrl/授权来源。链接只由已实现适配器或固定官方目录产生，不能从模型参数直接放行。
- 国内默认 Asia/Shanghai。境外适配器保留为历史代码/资料，不作为国内安排的自动库存来源。

### 接口与工具

- `GET /travel/domestic/providers`：官方渠道目录和当前接入状态，不返回秘密，不把「官网有能力」当「当前已开通」。
- `GET /travel/domestic/conversations/:id`：当前用户会话对应项目、方案集合与当前选择；无项目返回空态。
- `GET /trips/:id/domestic/options`：恢复该项目最近方案集合，说明是否已过期。
- `POST /trips/:id/domestic/options`：根据已保存候选生成并验证多套方案，要求 revision。
- `POST /trips/:id/domestic/options/:versionId/select`：校验当前集合、修订号与行程冲突，选择不代表订单。
- `journey_option_select`：仅在用户明确指定第几套时选择，编号与画布一致，恢复执行的只读工具不开放此写入。
- `POST /trips/:id/domestic/handoff`：按固定渠道生成查询/官方入口；只有真实适配器支持时才返回商品预订链接；记录导流动作，不标记成交。
- `journey_arrange`：绑定本账户会话，复用现有持久化聊天运行做有界采集＋组合＋保存，公开阶段说明；只读研究代理不能执行。
- 一键安排复用已有提交、取消、SSE 重放、运行租约；不是新建一套浏览器内假进度。

### 前端组件边界

- `JourneyDecisionBoard`：会话方案加载、当前选择与动作编排；composable 管理网络/身份竞态。
- `PlanChoiceCard`：一套方案的方式、关键取舍、预算完整性、活动/时长、选择入口；props 只读，emit 选择。
- `PlanTimeline`：当前已保存版本的逐日日程、警告和地点导航。
- `BudgetEvidencePanel`：冻结价格、数量、类型、查询时间、预备金和来源；不在浏览器重算权威预算。
- `BookingChecklist`：当前方案待预订类别、真实入口和不能确认的条件；不展示假的商品直达按钮。
- `DomesticProviderPanel`：可用与待开通渠道，说明没有数据的真正原因。
- 页面负责切换对话/方案视图。桌面主要空间用于方案，轨迹/对话按需展开；移动端纵向展示、地图另切换。输入框空闲紧凑、聚焦展开。

### 接入依赖与补充品类

授权接入按以下链路推进：开发者/企业资质与合作申请 → 确认分销品类、推广渠道及结算协议 → 获得文档、测试及生产权限 → 逐家适配商品搜索/分页/条件归一 → 同条件比价 → 跳转前验价与供应商正式取链 → 获准后才对接成交回调。商户商品管理权限、联盟推广权限和全平台搜索权限不能互相替代。公开文档不等于免费开放生产库存。

优先依赖：酒店/门票先申请美团分销及携程旅游；国内机票申请去哪儿、同程或其他已核实的国内供应链，获得至少两个实际渠道后才提供跨平台价格对比；餐饮/玩乐接美团联盟、合适的抖音推广场景；用车接用户授权的滴滴或商业出行合作。申请对象同时保留，不推断所有平台都能审批成功。

完整旅行还需覆盖以下边界，但当前不能把它们宣称为已聚合商品：

- 城际汽车、机场巴士、轮渡：同程公开有汽车票合作入口；具体线路、班次及船票另向运营方或获授权分销商确认，不用高德路线代替可售座位。
- 自驾能源、过路费、停车、充电：路线与POI由高德提供；油/电单价、充电枪状态、停车余位和节假日政策必须另有相应来源。没有能耗单价时先给真实路线，五类车辆费用保持未知；不伪造零元油费。城市中心路线须改精确地址后再作为门到门参考。
- 民宿、营地、房车、包车、演出、亲子活动、当地一日游：仅接合作渠道真正开放的SKU；特殊入场年龄、营业日期、最低成团人数、装备和退款规则分别建条件，不能用普通酒店或景点POI充当这些商品。
- 天气和临时公告、限行/闭园、接驳末班时间、退改售后：使用官方运营信息或对应供应商规则；有冲突时降级可行性，并给备用安排。保险仅作为需平台确认的可选服务，不混入默认费用或代为投保。
- 所谓“全量”应解释为“所接授权渠道在当前条件下返回的覆盖范围”；无法保证所有平台、会员价、优惠券、门店菜单和座位库存均可获取。

### 安全与隐私

身份从守卫取得。平台跳转只允许已登记 HTTPS 主机和已知入口，不允许任意外部 URL、认证参数或 javascript 协议。不对用户隐藏返佣关系。MCP Key 只在后端；商业签约密钥与个人乘客 Key 不混用。当前没有真实订单工具、付款工具或乘客证件托管。转换指标只能记录真实点击；没有平台回调就不知道是否成交。

## 5. Risks & Roadmap

实施顺序是依赖顺序，不是降低完整产品目标：

1. 写清本 spec 和供应商调研，建立明确授权依赖与验收标准。
2. 实现国内供应商目录/交接、方案集合契约、真实候选组合、上下文摘要与有界安排工作流。
3. 联通聊天和方案工作台，提供一键安排、比较/选择、时间轴、平台交接与更大的展示空间。
4. 覆盖真实基础工具和模拟供应商故障，完成格式/类型/自动回归、真实问答与浏览器验收。
5. 商业平台获得账号、合同、开发文档和生产权限后，逐家实现真实商品搜索/验价/链接适配并联调。该依赖不阻止其他工程实现，但未完成时必须保持待开通状态。

主要风险：商业权限与覆盖不保证、会员/优惠券造成条件差异、报价跳转后变化、未来出行路况只是估计、各平台同名门店/房型难以匹配、免费预约与营销团购混淆、个人 MCP Key 被错误共用、生成多个看似不同但实际重复的方案。
