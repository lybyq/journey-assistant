# 国内商品聚合与综合决策改造 Spec

状态：聚合核心尚未完成；本文件取代“渠道目录和三套行程即完成聚合”的判断。调研日期：2026-10-31。用户范围为各类国内个人出行，商业模式为免费规划＋预订导流。

## 1. Executive Summary

当前缺口是商品数据和比较能力。项目现有酒店主要为高德POI，餐饮主要为地点推荐；商业适配器只有历史Amadeus及旅行团网关，没有美团/艺龙等国内多源商品接口。本轮检查时，自驾只取第一条路线、忽略路线收费；这一项已修正并完成真实接口和页面核验。此前工程测试和编排完成不等于聚合核心完成。

目标是“先查可用供给，按相同条件比较，联合安排整趟行程，再带用户去对应商品”。AI负责澄清、解释和交互，价格、匹配、验价、排名与行程可行性必须有确定性系统支撑。

验收必须同时满足：

- 同一个酒店或景点商品取得至少两个独立生产渠道的有效报价，展示日期、人数、SKU、必要费用和退改条件；未达成时不称跨平台比价。
- 餐饮分别支持同店同套餐跨渠道比价，以及不同餐厅的就餐方案比较，不混淆人均、代金券、套餐和座位预约。
- 自驾同一起终点对比推荐、少收费、速度等实际路线，分别展示过路费、里程、耗时、能源假设和缺项；0元和未返回不能混用。
- 整趟旅行给出费用、耗时、体力、入住、营业预约及退改之间的明确取舍，调整一项后重新核对受影响内容。
- 商品跳转仍需携带供应商允许的条件；平台首页、商品详情、验价成功、已预订是四种不同状态。

### 用户看到的比较内容

- 酒店：同店→入住/离店→成人儿童和房间配置→具体房型/床型→餐食→退改→必要费用→总价→渠道。不同SKU只作不同方案，不能硬排成同商品最低价。
- 餐饮：实际门店、菜系/饮食限制、具体套餐适用人数、可用日期时段、预约/排队信息、距离接驳、参考人均与实际套餐价。不同平台评分分开展示，不直接平均。
- 景点：真实景区实体、票种、日期/场次、人群、有效期、预约和退改；含接送/讲解的联票不与单门票混排。
- 自驾：单程/往返范围、推荐/少收费/速度路线、车辆类型、里程、驾驶与休息时间、收费估算、燃油或电耗单价及依据、停车/充电/租车/保险。未来节假日减免、ETC优惠和实际出发日路况未确认时保留提示。
- 整体方案：酒店便宜但远带来的交通成本、景点的预约窗口与闭馆日、亲子/老人/行动限制的节奏、退改弹性、预算覆盖率及备用方案。

酒店、餐饮和景点需要分别有“商品列表”“同商品渠道报价”“加入方案”和“验证后打开商品”入口。原来固定首页的按钮保留查询用途，不计作商品导流已完成。

## 3. AI System Requirements

执行链路：需求与硬约束→按品类并行查询生产渠道→同实体映射→SKU/条件归一→剔除不可订、过期和不匹配价格→候选池→路线/营业/预约校验→费用与时间的多目标组合→真实差异方案→局部修改→验价→商品交接。

硬约束先于评分。综合排序考虑金额、门到门耗时、步行/驾驶、地理聚集度、营业预约冲突、房型人群政策、退改、来源可靠性和信息完整度。没有用户授权的时间价值时，不把“一小时”擅自换算为人民币；直接解释省多少钱、多花多少时间。采用非支配方案保留费用/时间/舒适之间的取舍，不强行凑三套，也不把佣金加入对用户的适合度排序。

上下文保存的是当前需求、选中的offerId/SKU、供应商条件、验价时间和版本依赖图。用户换酒店后，仅保留仍满足条件的交通/活动，重算接驳、预算、时间与预约风险；旧会员价、旧报价和旧确认不能沿用。

验证覆盖：同酒店异名、同名异店、含早与无早、可取消与不可取消、单晚与全程、儿童条件、过期报价、已售罄、条件变更、供应商部分失败、无收费字段与明确零收费、节假日未知、重选酒店引起的路线变化。

## 4. Technical Specifications

### 数据与系统边界

- 供应商适配器按真实能力实现`search/details/quote/revalidate/bookingLink`，每项能力独立报告是否开通，不能一项Token等同全部能力。
- `entities`与`provider_entity_links`维护门店/酒店/景区映射：供应商ID、地址、坐标、电话等做候选匹配；有歧义进入待确认，不能只凭名称合并。
- `offers`保存渠道SKU、查询条件、金额与单位、税费、库存、有效期、证据、适用人群、退改和可用入口类型。`conditionHash`包括当前入住/出行日期与人群/产品条件。
- `comparison_snapshots`冻结同口径比较；只有同实体且条件兼容的报价进入同组。会员、券、登录状态单独标识并按用户隔离缓存。
- 静态内容、查询缓存、实时产品和验价用不同生命周期；并发、速率、重试及缓存遵守对应渠道约定。授权失败不按“无库存”处理，网页摘要不升格成报价。
- `itinerary_dependencies`记录活动、交通和酒店之间的依赖；本地费用计算与可行性校验独立于模型。
- 链接由真实适配器产生；验价成功也不等于有可用商品跳转协议，更不代表已锁库存。返佣和成交回调仅在实际取得权限后实现。

### 已确认的当前代码缺口

`SupplierService`未实现国内酒店/餐饮/门票多源报价；`ExperienceService.places`只是地点；渠道目录只有状态。没有跨平台SKU归一和报价比较，尚不能宣传为完整聚合核心。

自驾原有的数据丢失已在本轮修正：无途经点查询通过高德Web服务比较推荐、少收费、速度策略，去重保存最多三条实际路线及收费，失败时回退MCP；费用只引用所选路线，已知小计不混入其他备选路线的费用。途经点仍走原有逐段查询，尚不具备全程多策略联合优化。完整验证与限制见[验证记录](../VERIFICATION.md)和[自驾学习链路](../DRIVING.md)。

## 5. Risks & Roadmap

实施依赖按以下顺序推进，不再把“卡片完成”当“比价完成”：

1. 已完成单起终点的路线数据修正：保留收费和多个真实路线，直连高德Web API并保留MCP回退，明确来源、单程范围与收费估算；已完成真实Key联调、页面核验与供应商协议回归。途经点联合优化仍待完成。
2. 建立实体、商品和条件模型以及比较接口；前端分别呈现商品和渠道报价，验证同条件分组、过期、条件变更和部分失败。
3. 接入至少两个获准的国内酒店生产渠道；只要缺少生产报价/商品入口，就继续标记该品类未完成。美团个人内容助手作为辅助，不替代结构化SKU供给。
4. 按相同原则接餐饮套餐、门票/活动，补商品验价和交接；确认链接与成交归因权限。
5. 用真实商品驱动联合优化与改选联动，补停车、充电、营业/预约、家庭成员、天气/限行等因素；取不到的数据明确来源与缺口。

工程可完成的数据模型、接口、错误隔离与组合计算先做；真实账号授权、接口额度、生产商品验证是实质依赖，不能用fixture或“待开通”列表冒充已经满足。
